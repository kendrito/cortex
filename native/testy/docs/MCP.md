# Testy as an MCP server

Testy's command-line tool contains a [Model Context Protocol](https://modelcontextprotocol.io/) server. Any MCP-capable agent harness on the same PC can start it and use Testy the way Testy's own built-in AI does: inspect a running Windows application (its control tree and a screenshot), perform single UI steps, create and update saved tests, run them, and read the recorded evidence. Everything the agent creates is written to the Testy workspace, so it appears in Testy Studio's library and Results immediately.

## Start the server

The server is `Testy.Cli.exe`, which lives next to `Testy.Studio.exe` in the portable bundle (`dist\Testy\`).

```text
Testy.Cli.exe mcp [--workspace DIR] [policy options]                                   stdio (default)
Testy.Cli.exe mcp --transport http [--port N] [--token T] [--workspace DIR] [policy options]  Streamable HTTP on loopback
Testy.Cli.exe mcp --describe [--format manifest|server-json] [--relative]              discovery manifest, then exit
Testy.Cli.exe mcp --help                                                               the options
```

- The default workspace is `%LOCALAPPDATA%\Testy\Workspace`, the same folder Testy Studio uses. `--workspace` selects another one; it is created when missing.
- **stdio** is the MCP stdio transport: JSON-RPC 2.0 messages, UTF-8, one message per line, no embedded newlines. A leading byte order mark and CRLF line ends are tolerated; a line may be at most 32 MiB (a longer one is answered with `-32700` the moment the limit is crossed, and the rest of that line is ignored). stdout carries only protocol messages; every log line and every startup error goes to stderr (log lines start with `[testy-mcp]`) and to `<workspace>\mcp\logs\mcp-YYYYMMDD.log`. The server exits with code 0 when its stdin closes, closing the apps it launched (unless `keepOpen` was requested). A wrong option, an invalid workspace or any other startup problem exits with code 2 and a JSON error on stderr; `mcp --help` prints the usage on stdout and exits 0.
- **HTTP** binds `127.0.0.1` and `::1` only. When ready it prints one JSON line to stdout, for example `{"transport":"http","url":"http://127.0.0.1:52341/mcp","port":52341,"tokenRequired":true,"pid":4242,...}`, and writes the same facts to `<workspace>\mcp\endpoint.json` (removed when it stops; its `pid` tells a reader whether the file is stale). `--port 0` (the default) picks a free port. The bearer token comes from the environment variable **`TESTY_MCP_TOKEN`** (preferred: a command line can be read by other programs of the same user) or from `--token T`, which wins when both are set; then every request must carry `Authorization: Bearer T`. The variable is ignored in stdio mode. The server runs until its stdin closes, the process named with `--parent-pid N` exits, or Ctrl+C; started with stdin from the NUL device (what "ignore stdin" means in most process libraries) it runs until it is terminated.
- **Policy options** (both transports): `--no-launch` (launch_app, run_test with `exe` or `app`, and the app tools with `launch: true` start nothing), `--allow-exe PATH` (only this program, or programs in this folder; repeatable; also the only way to allow a program that is part of Windows itself), `--allow-target NAME` (only this process name or exe path may be inspected and driven; repeatable). `get_workspace_info` and `--describe` report the active policy.
- **Retention**: evidence of a server session (`<workspace>\mcp\sessions\<session>`) older than 14 days and log files older than 30 days are removed when a server starts; the current session's never.

## Connecting a harness

Most MCP clients accept a configuration shape like this for a stdio server (it is a common convention, not part of the protocol):

```json
{
  "mcpServers": {
    "testy": { "command": "C:\\Tools\\Testy\\Testy.Cli.exe", "args": ["mcp"] }
  }
}
```

Add `"--workspace", "C:\\path\\to\\workspace"` to `args` to point the server at a specific workspace. A harness that connects over HTTP starts `Testy.Cli.exe mcp --transport http --port 0` with `TESTY_MCP_TOKEN` set in the server's environment, reads the startup line (or `<workspace>\mcp\endpoint.json`) for the URL, and sends its requests to that URL with the bearer token.

Three discovery aids let a harness (or an AI reading the bundle) recognize and attach to the server without help:

- `Testy.Cli.exe mcp --describe` prints a JSON manifest: the absolute command line for both transports, the framing, the options, the default workspace, the sample app path, the security statement, the launch policy, every tool with its description, the resources, prompts and supported protocol versions. Its `clientConfiguration.mcpServers.testy` is the ready form of the configuration above. `--format server-json` prints the same identity in the MCP Registry `server.json` shape; `--relative` makes the command relative to the exe's folder.
- `mcp-server.json` at the bundle root is that registry-shaped file: an identity card (`name`, `description`, `version`, `$schema`) with the local launch details under the registry's publisher-provided `_meta` key (`io.modelcontextprotocol.registry/publisher-provided`, entry `localServer`). Its `name` uses the namespace `io.testy`, a placeholder: whoever publishes the server to a registry sets `McpDescribe.RegistryNamespace` to a domain or account they control first. `mcp --describe` is the actionable source; the file only identifies the server.
- `AGENT-ACCESS.md` at the bundle root is a short factual note for an AI: requirements, how to start the server, how it speaks, what it offers and the rules that matter at run time.

## In Studio

Testy Studio works with the server without any product-specific setup; nothing in it is tied to a particular agent.

- **Settings › Agent access (MCP).** The card shows whether the server executable was found (`Testy.Cli.exe` next to Studio, or the development build), the exact stdio command an agent runs (`"…\Testy.Cli.exe" mcp --workspace "…"`, with **Copy command**), **Copy JSON** for the `mcpServers` shape above (with `--workspace` in `args`, and `DOTNET_ROOT` in `env` when the development build needs it), **Test the connection** (Studio starts a stdio server the way an agent does, sends `initialize` and `tools/list`, reports "Testy answered with N tools…" (every native and Cortex tool) in the status line and closes it) and **Open guide** (this document, or `AGENT-ACCESS.md` in the bundle; shown in its folder when no program opens `.md` files).
- **Listen for agents (HTTP).** With the switch on, Studio keeps `Testy.Cli.exe mcp --transport http --port <port> --workspace "…"` running as a child process with a bearer token of its own in the server's environment, and shows its loopback URL (**Copy URL**, **Copy HTTP JSON** for an `mcpServers` entry with the URL and the `Authorization` header). The **port** is remembered: 0 lets Windows pick a free one the first time, which is then kept, so an agent configured with the address finds it again after a restart; it can be changed in the card and takes effect at the next start (a port that is taken falls back to a free one with a note in Activity). The **token** is generated once per Windows user, shown only by its last characters, and copied whole with **Copy token**; requests without it get `401`. While listening, `<workspace>\mcp\endpoint.json` names the address. The switch is remembered per user; the listener starts again with Studio and stops when Studio closes (stdin closed, then a bounded wait for the server's own orderly stop; only the server process is ended, so apps an agent launched with `keepOpen` survive). A failed start turns the switch off for the session only. The server's log lines (stderr) appear in Studio's Activity pane under "Agent access": warnings and errors always, ordinary lines at a low rate.
- **Live updates.** Studio watches the workspace's `tests` and `runs` folders. A test created, changed or deleted by `create_test`, `update_test` or `delete_test` appears, changes or disappears in the library within about half a second (at most a second into a steady stream of writes), with an activity entry such as "Test “X” was added by an outside tool." If the changed test is open with unsaved edits (in any field, the JSON view or a cell still being edited), Studio keeps the edits and offers **Reload** or **Keep my edits**, and refuses to switch away, run or close until one is chosen; if the open test was deleted, it offers **Save a copy** or **Discard** (Save keeps it under its own id). A run saved by `run_test` refreshes Results and, for the open test, Last run ("Run of “X” finished (Passed) from an outside tool."), unless a run was opened on purpose, which stays. Studio's own saves are recognized by content and never reported as outside changes; a file still being written is read again on the next pass; a file with a byte order mark, explicit nulls or an invalid id is normalised or reported, never a reason for Studio to fail.

## Protocol

| Revision | How it is served |
| --- | --- |
| 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25 | `initialize` handshake. The server echoes a requested version it supports and otherwise answers with 2025-11-25. `notifications/initialized`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list`, `prompts/get`, `logging/setLevel`, `notifications/cancelled`, `notifications/progress`. JSON-RPC batch arrays (2025-03-26) are accepted and answered with one array in request order (no line at all when every entry was a notification or was cancelled); `initialize` inside a batch, and an entry of the 2026-07-28 revision, get a `-32600` entry. |
| 2026-07-28 | Stateless: each request declares `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` (an object) in `params._meta`; `clientInfo` (name and version) and `logLevel` are validated when present. A request that belongs to this revision (by its `_meta`, by the HTTP `MCP-Protocol-Version` header, or because it is `server/discover` or `subscriptions/listen` on a connection without a handshake) without those fields is `-32602` (HTTP `400`). Results carry `resultType`, `_meta.io.modelcontextprotocol/serverInfo` and cache hints; `server/discover` lists the supported versions. `initialize`, `ping` and `logging/setLevel` are not part of this revision (`-32601`, HTTP `404`; the `initialize` refusal names the supported versions). `subscriptions/listen` is served (see below). Unsupported versions get error `-32022` with the supported list. |

Both eras are served by the same process at the same time; the server picks the behaviour from how each request opens. Every message is registered in arrival order, so a `notifications/cancelled` written right after its request always finds it, and a request written right after `initialize` sees the negotiated version. Capabilities: `tools`, `resources` (no subscriptions, no list-changed notifications) and `prompts`; `logging` for the handshake revisions.

Errors follow JSON-RPC: `-32700` parse error (id `null`; also for a line that is not valid UTF-8), `-32600` invalid request (including a duplicate in-flight id and a numeric id with a fraction), `-32601` unknown method, `-32602` invalid params (including an unknown tool name and a `progressToken` that is neither a string nor an integer), `-32603` internal error, and the application-defined `1001` when the server has no free session or subscription stream (HTTP `503`). A tool that cannot do its job is **not** a protocol error: the result has `isError: true` and a text message that says what to do instead (for example "Testy is running another test on this desktop; try again in a moment"). Requests may carry `_meta.progressToken`; `run_test`, `launch_app` and the app tools that start a named app (`launch: true`) then send `notifications/progress` while they work (at most one per 100 ms per token, the newest value; every value increases and never passes the total; a run's messages name its run id).

**Cancellation** follows the specification strictly: `notifications/cancelled` stops the in-flight request with that id, and the server sends **no response** for it, whatever the handler produced meanwhile, and no further progress. Over stdio nothing more is written for that id; over HTTP the SSE stream simply ends, and a request that was not streamed ends with `204` and no body (the transport-level end of a cancelled request). The effect stays visible: a cancelled `run_test` leaves its run in `list_runs` and `get_run` with status `cancelled` and the steps after the cancelled one skipped (call `list_runs` with the `testId`; the run id is also in every progress message); a cancelled `perform_step` is described by `lastCancelledStep` in `get_workspace_info`. The server never retries mutations, so inspect the app before repeating a step whose call was cancelled.

**`subscriptions/listen`** (2026-07-28): `params.notifications` must be an object whose `toolsListChanged`, `promptsListChanged` and `resourcesListChanged` are booleans and whose `resourceSubscriptions` is an array of URI strings (`-32602` otherwise). The server first sends `notifications/subscriptions/acknowledged` with the request id as `io.modelcontextprotocol/subscriptionId` and an empty `notifications` object (it offers no notification type), then holds the request open. A client cancels it with `notifications/cancelled` (stdio) or by closing the stream (HTTP), after which nothing more is written. When the server stops it sends `notifications/cancelled` for the request and then the completion result (`resultType: complete`, the subscription id and `serverInfo`). At most 16 streams are open per process (`1001` beyond that). Over HTTP the answer is an SSE stream; without `text/event-stream` in `Accept` it is `406`.

**Over HTTP**: `POST http://127.0.0.1:<port>/mcp` with a single JSON-RPC message and `Content-Type: application/json` (any letter case, parameters allowed, charset only UTF-8; anything else is `415` and the body is not read). A body larger than 32 MiB is `413`, decided while it is read (a chunked body is refused as soon as the limit is crossed); a leading byte order mark is tolerated. Handshake revisions receive an `Mcp-Session-Id` header on `initialize` and must send it on every later request (`400` when missing, `404` when unknown or expired after 10 idle minutes; idle time counts from the end of a session's last request, so a long run never expires its session); `initialize` with a valid `Mcp-Session-Id` replaces that session with a fresh one; at most 64 sessions are open at once (`503` with code `1001` beyond that); `DELETE` with the header ends the session; `GET` is `405` because the server initiates no messages of its own. `tools/call` and `subscriptions/listen` are answered as an SSE stream (`event: message` events with progress notifications, then the response, with a keep-alive comment every 2 s) whenever the `Accept` header lists `text/event-stream` with a quality above zero, with or without a progress token; `*/*` alone, a missing `Accept` header or `application/json` keep the JSON answer. **Closing the stream cancels the call** in every revision, which for the handshake revisions deviates from the 2025-11-25 sentence "Disconnection SHOULD NOT be interpreted as the client cancelling its request": this server has no resumable streams, and a call that keeps sending input to the desktop after its caller is gone would be worse. A request is validated before any status is written, so a malformed request is `400` and an unknown method `404` as plain JSON even when a stream was asked for. Revision 2026-07-28 requests carry `MCP-Protocol-Version`, `Mcp-Method` and, for `tools/call`/`resources/read`/`prompts/get`, `Mcp-Name` headers that must match the body (`400` with `-32020` otherwise; a body without the field the header mirrors is the method's own `-32602`); their `notifications/cancelled` stops the in-flight request with that id when exactly one has it. `Origin` is accepted when absent (a program, not a browser page) or when it is `http`/`https` with the host `localhost` or a loopback address; `null`, extension schemes and look-alike hosts such as `localhost.evil.com` or `127.0.0.1.evil.com` are `403`, as is a `Host` header that is not loopback. A missing or wrong bearer token is `401`. Log lines name a session by the first characters of its id and never contain the token.

| `get_workspace_info` | Workspace paths, Testy version, provider kind (never secrets), sample app path, counts, the apps this server launched, runs in progress, desktop state, the launch policy, the last cancelled step, selector syntax, the action catalog, complete examples and the coordinate contract. Call it first. |
| `list_tests` | Saved tests with each test's most recent run. |
| `get_test` | One test with all its steps. |

It appears in Studio at once. `app` names the app the test runs in ("Customer Desk" or an exe path); it is resolved like `find_app` and stored as `targetPath`, `targetName` and, for a packaged app, `targetAppId`. Returns warnings (no assertion, a select without a value, a name another test already has: names are not unique). |
| `update_test` | Change name, intent, category, the app (`targetPath` or `app`; an empty `app` clears it) or steps (steps replace all; keep step ids to preserve them). |
| `delete_test` | Remove a saved test (runs stay in Results). |
| `validate_test` | Check a candidate without saving; takes what create_test takes (an `app` that does not resolve to one app is a problem); returns every problem and the warnings. |
| `list_apps` | Windows on this PC that Testy can connect to (title, process, pid, exe path when readable, whether minimized, whether this server launched it). |

Bound to the server's job object, so it ends with the server however the server ends, unless `keepOpen`. |
| `close_app` | Closes an app this server launched (main window close; `force` ends the process). |
| `activate_app` | Restores a minimized window and brings it to the foreground (`pid` or `app`). |
| `inspect_app` | Control tree (selector, controlType, depth, name, value, bounds `[x,y,w,h]`, `center` for coordinateClick, and only when not the usual value: enabled, offscreen, automationId, capabilities, childCoverage, password, valueTruncated) plus a screenshot. Defaults to 150 on-screen controls; `filter`, `within`, `offset`, `includeOffscreen`, `selector` (one control in full, with its properties) and `details` shape the result. Reading stops after 2000 controls, 30 levels or 10 s (`treeTruncated`). |
| `screenshot_app` | PNG of the app's windows with its bounds and scale. |
| `perform_step` | Execute exactly one bounded step against a pid (or `app`). A step takes about its `timeoutMs` at most (default 5000; keep it at 40000 or below to stay inside a 60-second client limit). Returns outcome, diagnostics, what the step changed (`observation`: `changed` by default, `full` or `none`) and a screenshot. Evidence goes to `<workspace>\mcp\sessions\`; nothing is added to Results. |
| `run_test` | Run a saved test through Testy's runner (deterministic replay, or `mode: "ai"` with the configured provider) against a pid, a program started for the run (`exe`, under the launch_app rules, with `args`, `workingDirectory`, `waitForWindowSeconds`, `keepOpen`), or an app named in words (`app`: a running instance is used, else the program is started for the run). With none of them, the app stored on the test is used the same way; a test without one is an error that says how to name it. An app started for the run is closed afterwards unless `keepOpen`. Saved via the workspace, so it appears in Studio's Results. Waits up to `waitSeconds` (default 45, 0–900) for the result; a longer run, or `wait: false`, returns `status: "running"`, `running: true`, the `runId` and the steps completed so far (`completedSteps`) while the run continues in the background, with the guidance to call `get_run` with `waitSeconds`. Cancelling the waiting call cancels the run. `running` turns false as soon as the result is recorded; an app the run started is closed right after, and the next UI call waits a few seconds for that ("Testy is closing the app it started for the run …"). |
| `cancel_run` | Stops a run in progress (started with `wait: false`, or one that outlived its call) through the same path as `notifications/cancelled`, and returns it with status `cancelled` (or with its own final status and a message that says so when it finished before the cancellation took effect). A run whose result is already recorded is reported as finished (`isError`, nothing changes). |
| `list_runs` | Recent runs, optionally for one test, in-progress runs included. |
| `get_run` | Full run: per-step status, duration, runner message, failure diagnostics, AI notes, screenshot availability. `waitSeconds` (0–45, default 0) waits until a run in progress has recorded its result or the time is up (a long poll), so an agent does not call it in a loop. A final status is never reported with `running: true`. |
| `get_run_screenshot` | The PNG recorded after a run step (1-based step number), only from the run's evidence folder inside the workspace. |
| `find_app` | Resolve an app named in words (`query`; `includeInstalled`, default true; `limit`, default 10) to ranked candidates: `kind` (`running`, `installed`, `recent`, `sample`), `name`, `windowTitle`, `pid` (when running), `exePath`, `appId` (packaged apps), `confidence`, `level` and `reason`; `status` is `unique`, `ambiguous` or `notFound`. Starts nothing. |

`find_app` is listed after the earlier tools (and before the Cortex tools of this build), so their order is unchanged. Every argument and result field of the earlier tools is still accepted and returned as before; the additions are optional (`app`, `launch`, `get_run` `waitSeconds`, the wider `run_test` `waitSeconds` range) or new result fields (`resolvedApp`, `completedSteps`, `targetName`, `targetAppId`). `pid` is no longer required by `inspect_app`, `screenshot_app`, `perform_step` and `activate_app` (one of `pid` or `app` is), nor `exe` by `launch_app` (one of `exe` or `app` is).

### Naming the app

An agent can name the app the way the task does ("In Customer Desk, add a customer…") instead of finding a pid first. `app` is accepted by `inspect_app`, `screenshot_app`, `perform_step`, `activate_app`, `launch_app`, `run_test`, `create_test`, `update_test` and `validate_test`; `find_app` shows how a name resolves.

- **Candidates.** Running top-level windows (visible, titled, not cloaked, not owned tool windows): title, process name, exe path, and the product name and file description from the program's version resource. Installed desktop apps: Start menu shortcuts of the current user and of all users (resolved through the Windows Script Host shell object; a shortcut with arguments opens something with a program and is not an app of its own) and the App Paths registrations under HKCU and HKLM. Packaged (Store/MSIX) apps from the shell's Applications folder (`shell:AppsFolder`), with their AppUserModelID. The apps earlier tests store (`targetPath`, `targetName`, `targetAppId` across the workspace). Testy's sample apps next to the server (Customer Desk, Order Desk and WPF Control Lab: their names come from the programs' own version resources). A program an earlier test stores is looked at only when its path is a full local drive path: a test file can come from anywhere (restored, imported, synced, edited), and opening a network path would already authenticate this user to that host, so such a path is never opened; `run_test` with the test's stored app refuses it with a message instead. Entries for one program are merged (a running instance takes the names of its shortcut, sample or earlier test); installed apps are cached for three minutes.
- **Scoring.** An exact name (display name, product name, window title or a part of it such as the "Word" of "Report.docx - Word", shortcut name, exe name) scores 1.0 (0.98 on a secondary field such as a title part, file description or process name); a prefix of whole words 0.85, the start of a word ("Calc") 0.8; the name as whole words inside a longer name 0.75; partial word overlap (one typo allowed in words of five letters or more) at most 0.65. Case, accents, punctuation, `.exe` and filler words ("the", "app", "window") do not matter, and camel case counts either way ("TestLab" = "test lab" = "testlab"). Running instances rank first among equals.
- **Unambiguous** means one candidate with confidence 0.7 or more and no other candidate within 0.1 of it; among exactly equal best scores a single running instance wins when it is named as a program (its display name, product, shortcut or exe name, not merely its window title) or when every contender is that same program. A window whose title only reads like the name (a folder, a browser or terminal tab titled "Customer Desk") is another program, so an installed "Customer Desk" and such a window stay ambiguous. Anything weaker is `notFound`, anything closer is `ambiguous`, and the tools that take `app` then answer `isError` with the candidates as compact JSON (kind, name, pid, exePath, confidence, reason) so the agent can pass one's `pid` or a more precise name. Two running instances of one program are ambiguous to connect to but one program to start or store. Nothing is ever started or connected on a weak or ambiguous match.
- **Starting.** A named app that is not running is started only by `run_test`, `launch_app`, or an app tool with `launch: true`, under exactly the launch policy of `exe` (Safety) and in the same cleanup job. The result's `resolvedApp` says which app was used (`pid`, `exePath`, `kind`, `confidence`, `reason`) and whether Testy started it (`launched`).
- **Packaged apps.** Their running windows are found and connected to like any other; a classic UWP app's window belongs to the ApplicationFrameHost process, so when several such apps are open Testy may connect to the frame of another one (close the others). Starting one is best effort: Testy reads the program the package manifest names for that application and starts it through Windows' activation manager only when that program passes the launch policy; Windows starts the process, so it joins the cleanup job only afterwards and only when Windows allows it (otherwise it is closed through its window when the server exits); a single-instance app may answer with the process that was already running, which Testy then never closes.

### Time limits

Many MCP clients abort a `tools/call` after 60 seconds (the official SDKs default to 60 s), so every call answers within about 45 s by default: `run_test` waits `waitSeconds` (default 45) and then answers `status: "running"` while the run goes on; `get_run` with `waitSeconds` (up to 45) waits for the end; `cancel_run` stops a run whose call has answered. `launch_app` waits `waitForWindowSeconds` (default 20); when `run_test` starts the app and its window takes longer than `waitSeconds`, the call answers once the run has started. `perform_step` takes about its `timeoutMs` (default 5000); `inspect_app` stops reading after 10 s; `find_app` scans installed apps within about 30 s at most the first time and uses its cache afterwards. Progress notifications continue while a call is open. The server's instructions also tell agents not to use any other desktop-control tool (mouse or keyboard automation) while a Testy run or step is in progress, because both would fight over the same input.

Every tool has an `inputSchema` (object, `additionalProperties: false`), an `outputSchema` that declares every returned field (status fields are enums; `additionalProperties: true` for later versions), and annotations: `readOnlyHint` (false for every tool that can start a program: `launch_app`, `run_test`, and `inspect_app`, `screenshot_app` and `perform_step`, which start the named app with `launch: true`; so a client that approves read-only tools without asking still asks before a program is started), `destructiveHint` (true for everything that sends input, can start or end a program, or changes a test), `idempotentHint` and `openWorldHint` (true for every tool whose result carries content produced by other applications, and for the tools that can start a program). The earlier argument names `id` (for `testId`/`runId`) and `screenshotMaxWidth` (for `maxWidth`) are still accepted. Results contain the structured data and the same JSON as text: compact, with quotes, apostrophes, angle brackets and non-ASCII text written literally, so selectors and expected values can be copied as they are. Image results add an `image/png` content item scaled to `maxWidth` (coordinates for `coordinateClick` are in the unscaled source pixels relative to the top-left of the app screenshot; each on-screen element carries that point as `center`; the result reports the `scale`).

Resources: `testy://workspace` (JSON summary), `testy://docs/mcp` (the agent guide), and the templates `testy://tests/{id}` and `testy://runs/{id}`, which return the same views as `get_test` and `get_run` (a run without its per-step control trees; the full evidence is in `artifactDirectory`). Prompt: `write_test` with arguments `app` and `goal` produces the recommended authoring workflow.

## Steps and selectors

Steps use the same schema and action enum as Testy's built-in planner: `action`, `selector`, `value`, `timeoutMs` (100–60000, default 5000), `x`, `y`, optional `id` and `title`; for example `{"action":"typeText","selector":"id:CustomerName","value":"Ada"}`. The actions are `click`, `typeText`, `select`, `toggle`, `assertText`, `assertExists`, `assertNotExists`, `assertEnabled`, `wait`, `screenshot`, `keyPress`, `coordinateClick`, `expand`, `collapse`, `realizeItem`, `scrollIntoView`, `scrollPercent`, `assertProperty`, `assertItemExists`, `assertItemAbsent`, `gridEditCell`, `gridCommitRow` and `gridCancelRow`; `get_workspace_info` explains each one's value contract, which capability an advanced action needs, and the rules that decide whether a step works: `assertText` compares the control's value when it has one (always for Edit, TextBox, ComboBox and Document controls) and otherwise its name, exact and case-sensitive (prefix the value with `contains:` for a substring); `click`, `typeText`, `select`, `toggle` and `keyPress` need a control that is enabled and on screen (`scrollIntoView` first); `keyPress` takes 1–4 keys joined with `+` from ENTER, TAB, ESC, SPACE, BACKSPACE, DELETE, INSERT, HOME, END, the arrows, PAGEUP, PAGEDOWN, F1–F12, A–Z and 0–9 with CTRL/SHIFT/ALT, and refuses Windows-key chords, ALT+TAB, ALT+F4, ALT+ESC and CTRL+ESC; `toggle` takes on/off, true/false, checked/unchecked, 1/0 or an empty value (flip). `validate_test` and `create_test` refuse what cannot run. Assertions poll until the timeout; mutations are dispatched once and never retried.

Selectors are exact and case-sensitive:

- `id:<AutomationId>`: must match exactly one control across the app's windows. Preferred.
- `name:<Name>`: the accessible name.
- `path:<windowIndex>/<childIndex>/…`: structural position from `inspect_app`; brittle.
- `query:{"type":"Button","label":"Save","ancestor":{"id":"OrderDialog"}}`: `id` matches AutomationId, `type` the control type, `label` the Name; all supplied fields must match (AND); every object needs at least one of them; `ancestor` matches any strict ancestor and may nest up to 8 levels; no other keys; at most 2048 characters.

## Safety

- **What the server can do.** It can start desktop (GUI) programs the caller names (by path, or by a name it resolves to one program) and send keyboard and mouse input to any application the caller names by pid or name, with the rights of the user who runs it. It is not limited to Testy's own files: treat an agent that can reach it as an agent that can operate this desktop.
- **Launch policy.** `launch_app`, `run_test` (`exe`, `app` or the test's stored app) and the app tools with `launch: true` start only an existing `.exe` given as a full local drive path (or resolved to one) whose PE header declares the Windows GUI subsystem; a packaged app only when the program its manifest names passes the same checks. Console programs are refused by their header. Shells, script hosts, terminals and the program launchers Windows ships (which start whatever program their arguments name) are refused by name and by the name in their version resource, so a renamed copy is caught: `cmd`, `powershell`, `pwsh`, `wscript`, `cscript`, `mshta`, `rundll32`, `regsvr32`, `msiexec`, `conhost`, `wsl`, `bash`, `windowsterminal`, `wt`, `openconsole`, `explorer`, `pcalua`, `powershell_ise`, `hh`, `mmc`, `msdt`, `runas`, `forfiles`, `cmstp`, `presentationhost`, `scriptrunner`, `syncappvpublishingserver`, `appvlp`, `infdefaultinstall`, `mavinject`, `installutil`, `msbuild`, `regasm`, `regsvcs`, `wmic`, `schtasks`, `bitsadmin` (`get_workspace_info` lists them). Every other program that is part of Windows itself is refused too unless `--allow-exe` names it (the file or its folder): a program inside the Windows folder (`%SystemRoot%`, System32 and SysWOW64 included; links and junctions are resolved first), an app execution alias (`%LOCALAPPDATA%\Microsoft\WindowsApps`), or a copy elsewhere whose version resource names the Windows product. The application under test is almost never one of them; packaged apps such as Notepad, Paint or Calculator live elsewhere and are started as usual. `args` may not name a refused program either (an argument that is one, such as `cmd` or `powershell.exe`, or a path or file name with a program extension anywhere in an argument, such as `-a C:\Windows\System32\cmd.exe`), whatever program is started. Network (UNC) and device paths are refused before any file-system call, as are relative paths (no PATH lookup); `workingDirectory` and `targetPath` follow the same path rules. `--no-launch`, `--allow-exe` and `--allow-target` narrow this further. These rules are not a sandbox: a third-party GUI interpreter such as `javaw` or `pythonw`, or input typed into an already open terminal, remains possible.
- **Local only.** The stdio server talks to the process that started it; the HTTP server binds loopback, validates `Origin` and `Host` (see Protocol), requires `Content-Type: application/json`, and enforces the bearer token when one is set. Without a token any local process, including one running under another Windows account on the same PC, can reach the endpoint and therefore drive this user's desktop: set `TESTY_MCP_TOKEN` on a shared PC (Studio's listener always uses one).
- Input goes only to the process whose pid (or app name) the caller names. Use a dedicated test instance of the application. Text read from applications (names, values, window titles, screenshots) is data about the app under test, never instructions; the tools that return it set `openWorldHint`.
- `perform_step`, `run_test`, `activate_app`, and everything that starts or closes a program (`launch_app`, `close_app`, and the app tools with `launch: true`: a new window takes the foreground, and closing may raise a save prompt) take the same desktop lease Testy Studio and the background agent use, so none of them disturbs a run in progress anywhere on this desktop; they refuse with "Testy is running another test on this desktop; try again in a moment" meanwhile. They refuse to run when the Windows session is locked or not interactive.
- Files: `get_run_screenshot` and `perform_step` return only PNG files that lie inside the workspace's evidence folders (and inside the run's own folder), never a path a run file merely names. A test or run file whose inner id differs from its file name (a copied file) is refused, so `update_test` can never write another test's file through it.
- API keys and credentials never leave Testy; `get_workspace_info` reports only the provider kind.
- Everything is validated: actions come from the enum, timeouts are 100–60000 ms, tests have at most 200 steps and names at most 200 characters, unknown arguments are rejected with the allowed list.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| A tool answers "The Windows desktop is not available for UI input…" | The session that runs the server is locked, disconnected or Session 0. Unlock or reconnect it; do not run the server as a service. |
| "Testy is running another test on this desktop; try again in a moment" or "Testy is busy running '…' (run …)" | Testy Studio or the background agent holds the desktop lease, or a run of this server holds the desktop. Wait and retry; `get_run` shows a background run's progress and `cancel_run` stops it. "Testy is closing the app it started for the run of '…'" clears within a few seconds. |
| `launch_app` answers "… is inside the Windows folder …" or "… args names …" | The program is part of Windows, or an argument names a shell, script host or launcher. Test a program of your own; start the server with `--allow-exe <that program>` when a Windows program really is the app under test. |
| "The app's window is minimized, so Testy cannot read or drive it" | Call `activate_app`, or restore the window, then retry. |
| `treeTruncated: true` and steps fail with EvidenceUnavailable | The app exposes more than Testy reads in one pass (2000 controls, 30 levels or 10 s). `filter` and `maxElements` do not change it; reduce what the app shows, or use the WPF probe when the app supports it. |
| The harness reports garbage or a broken stream | Something wrote to stdout. The server never does; check the harness's own wrapper. Logs are on stderr and in `<workspace>\mcp\logs`. A byte order mark at the start of stdin is tolerated. |
| A tool answers that an app name "matches 2 apps about equally well" (or "No app clearly matches") | The name is ambiguous or unknown. Pass the `pid` of one of the listed candidates, or a more precise name (its full name, window title or exe path); `find_app` shows the ranking. |
| `run_test` answers `status: "running"` | The run takes longer than `waitSeconds`. Call `get_run` with the `runId` and `waitSeconds` (up to 45) until `running` is false; `cancel_run` stops it. |
| `launch_app` fails with "showed no visible titled window" or "cannot be started" | The program exited, started another process, needs longer, or is not a desktop program (console, script host, refused path). Raise `waitForWindowSeconds`, or start it yourself and connect with `list_apps`. |
| The server exits right after its startup line (HTTP) | Its stdin reached end of file: the harness closed the pipe. Keep the pipe open, start it with stdin from the NUL device, or pass `--parent-pid`. |
| HTTP `401`, `403`, `400`, `404`, `413`, `415`, `503` | Missing/wrong bearer token; non-loopback `Origin`/`Host`; missing `Mcp-Session-Id`, a malformed 2026-07-28 envelope or mismatching headers; unknown or expired session — send `initialize` again; body above 32 MiB; body not `application/json`; no free session or stream. |
| `mode: "ai"` is refused | No AI provider is configured in Testy Studio › Settings (Offline). Use `mode: "replay"`. |

Verification: `Testy.Cli.exe verify-mcp --lab Testy.TestLab.exe --artifacts <dir>` exercises both transports end to end against the sample app; see [TESTING.md](TESTING.md).
