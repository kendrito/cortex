# Backend integration contract for the redesigned studio

The primary **Run** workflow (AutomationId `RunTest`) is governed by the LLM after every action. Studio now uses `TestExecutionService`, which routes to `AiTestRunner` by default. The original `TestRunner` remains an explicit deterministic replay mode. Studio's look is the .NET 9 WPF Fluent theme plus a small Testy design layer; see [Theme and shell](#theme-and-shell).

## Primary run button

```csharp
using Testy.Core;
using Testy.Windows;

var nativeInput = new NativeComputerActionExecutor(attachedDriver);
var runner = new TestExecutionService(attachedDriver, providerSettings, artifactsRoot, nativeInput);
RunResult result = await runner.RunAsync(selectedTest, progress, cancellationToken);
store.SaveRun(result);
```

`progress` is `IProgress<RunProgress>`; `RunProgress.Step` contains a real observed action result and a screenshot path. Use `new Progress<RunProgress>(...)` on the UI thread. `RunResult` works with the same timeline, evidence, history, and reports as deterministic execution. `AiAnalysis` contains the model's final explanation. Set the UI busy state across the entire call. Keep a Stop button linked to the passed cancellation token.

`TestExecutionService` routes to `AiTestRunner` when `AiDirectedExecution` is true (the default) and to `TestRunner` only when the user explicitly chooses deterministic replay. An Offline provider with AI mode enabled is rejected with an explanatory message.

## Provider routing

- `ProviderKind.OpenAI` + `NativeComputerUse = true`: OpenAI Responses native `computer` input, plus `verify_saved_assertion(stepId)` and `perform_saved_control_step(stepId)` for explicit advanced WPF operations. The control tool cannot replace ordinary physical input.
- `ProviderKind.OpenAI` + `NativeComputerUse = false`: Responses custom local computer tools.
- `ProviderKind.Compatible`: compatible Chat Completions custom local computer tools.
- `ProviderKind.Codex`: authenticated Codex CLI chooses one local tool action per turn; this is the temporary no-API-key bridge.
- `ProviderKind.Offline`: no LLM; use explicit deterministic replay. Never label offline execution as AI-directed.

New persisted `ProviderSettings` properties:

```csharp
bool AiDirectedExecution = true;
bool NativeComputerUse = true;
int MaximumAgentTurns = 30; // allowed range 1..40
bool SupportsImages = true; // disable for text-only compatible models; native mode needs images
```

Do not infer native computer support solely from a name containing `gpt`; the configured model must support the tool. API errors remain visible. There is no silent fallback to a different provider or model.

## Verification semantics

The model sees the current screenshot and UI tree, chooses exactly one action, receives its result, and then decides again. Saved steps and assertions remain immutable. A run is Passed only when the model finishes and every saved workflow step and assertion was observed in its original order. Bound local tools retrieve the canonical definition by saved step ID. Native physical actions mapped to saved controls also require the exact runtime control's synchronized-input delivery acknowledgement. Explicit advanced WPF tools verify their saved semantic operation separately; they cannot bypass unverified earlier input. One unrelated passing assertion, a textual claim of success, a skipped interaction, or a weaker check cannot grant a pass.

Mapping native physical input to saved semantic controls requires the UIA driver and synchronized-input support in the target provider. Use local tools for ordinary probe interactions; its `wpf:` visual identities are not UIA runtime identities. Advanced operations use their explicitly named semantic tool and are not claimed as physical input. Unsupported delivery evidence produces an explanatory failed result. Present that result faithfully and keep provider errors visible.

AI-directed tests require at least one saved assertion and at least one model turn per saved step plus a completion turn. Native saved waits cannot exceed 5,000 ms. `AiTestRunner.ValidateExecution(test, settings)` performs public preflight; surface its errors before starting a suite or run. Plans remain editable before execution. Natural-language test authoring uses `PlannerFactory.Create(...).CreatePlanAsync(...)`; do not automatically execute a generated draft from the authoring button.

## Existing APIs

- `WorkspaceStore` has `LoadTests`, `SaveDraft`, `SaveTest`, `DeleteTest`, `LoadRuns`, `SaveRun`, `LoadSettings`, and `SaveSettings`. Use **SaveDraft** while editing incomplete tests. `SaveTest` performs complete validation.
- `UiAutomationDriver` / `WpfProbeDriver` implement `ITargetDriver`, including target enumeration, `AttachAsync`, snapshots, and captures, plus `IItemLookupDriver` for supported read-only collection lookup.
- `TestRunner` is deterministic replay. Its optional `StepObserver` is for commentary; it does not govern execution. Do not describe this as the primary AI-directed loop.
- `AiTestRunner` is AI-directed execution with verified saved acceptance criteria.
- Preserve the automation IDs listed under [AutomationIds](#automationids). The Studio verifiers select controls by these IDs, and every ID must stay unique across all windows and hidden pages.

## Theme and shell

This describes the redesign ("Native Windows"): a first-party Windows 11 look that follows the system theme and accent. Phase 1 set up the theme and shell; Phase 2 rebuilt the Tests page, added the Last run view with the run trace, the activity log, global search and the keyboard shortcuts (see [Tests page and Last run](#tests-page-and-last-run-phase-2)).

### Theme

- `App.xaml` sets `ThemeMode="System"`. WPF merges `PresentationFramework.Fluent` (Fluent control styles, light/dark from Windows, the Windows accent color, and the Mica backdrop). XAML usage raises no WPF0001 diagnostic; `App.xaml.cs` suppresses WPF0001 with a targeted pragma where it overrides `ThemeMode` at runtime.
- Hidden option `--theme system|light|dark` (default `system`) forces a theme for screenshots and reviews.
- The Fluent `Window` style makes window backgrounds transparent so Mica shows. Never set `Window.Background`; put content on the layer and card brushes below.
- Standard controls (Button, TextBox, ComboBox, CheckBox, PasswordBox, ScrollViewer, ToolTip, ContextMenu, Expander) use the Fluent styles. App.xaml adds only what Fluent lacks, and every color is a Fluent resource referenced with `DynamicResource` (in code: `SetResourceReference`), so light, dark, high contrast and live theme changes all work. Do not add hard-coded colors.
- Pass and fail never use the accent: they use `SystemFillColorSuccess/Critical/Caution` plus an icon and a word (`StatusPill`, `StatusNode`, the InfoBar severities). The accent marks selection (pills), the primary action and focus only.
- Fonts: `UIFont` (Segoe UI Variable Text), `DisplayFont` (titles), `SmallFont` (captions), `MonoFont` ("Cascadia Mono, Consolas"; Consolas is the fallback when Cascadia Mono is missing), `IconFont` (Segoe Fluent Icons, Segoe MDL2 Assets). Body text is 14 px, captions 12 px, page titles 28 px.
- .NET 9 Fluent quirks handled in App.xaml: the Fluent TextBox stretches its content, which WPF turns into *justified* wrapped text, so `TextBoxBase` (and the implicit TextBox style) pins `TextAlignment=Left`; the implicit ComboBox style reduces the padding so ComboBoxes match the 32 px height of text boxes and buttons.

### Shell

- `MainWindow`: Title "Testy" (never empty). Column 0 is the navigation pane over Mica (240 px; below 1280 DIP window width it becomes a 56 px icon pane, the items stay and their labels move to tooltips). Top items: Tests (`NavLibrary`), Results (`NavRuns`), Automate (`NavWorkflows`); footer: Help (`NavHelp`) and Settings (`NavSettings`). No hamburger.
- Column 1 is the content layer: the app bar (56 px), the pages, and a slim status line (`StatusText` on the left, `ContextStatus` on the right) where every status message still appears.
- App bar: the connected-app card (initials tile, app name, `TargetStatus` "Connected"/"Not connected"; the process ID and the program's file name show only with technical details on, the full path in the tooltip), **Change app ▾** (`ChangeApp`) opening a flyout with `TargetPicker`, `RefreshTargets`, the WPF helper checkbox, `AttachTarget` ("Connect") and `OpenExe` ("Open an app…"), then **Sample app** (`LaunchLab`), **Inspect controls** (`NavInspector`), the global search box (`GlobalSearch`, Ctrl+K), **Activity** (`ActivityButton`) and the **Show technical details** switch (`ShowTechnicalDetails`). Below 1440 DIP (1600 with technical details on and an app connected) Sample app, Inspect controls and Activity show icons only and the switch drops its label; their accessible names stay.
- Global search: typing in `GlobalSearch` lists matching tests (names first, then purposes, then step text) in a Popup under the box (`GlobalSearchResults`, a ListBox whose ListItem names are test names; it exists only while open). Up/Down move the highlight, Enter opens the highlighted test, and a click or a UI Automation Select on a result opens that test (Steps view, the matching step selected) and clears the box.
- Activity: `ActivityLog` (ActivityLog.cs) keeps the latest 500 entries in memory and appends each one to `%LOCALAPPDATA%\Testy\Logs\studio-YYYYMMDD.log` (one open/append/close per entry, so several Studio processes share the file; each line carries the process ID and, for run entries, the run ID). Every status line message (`SetStatus`), assistant reply, error (`ReportError`), save, run start, each step's start and result ("Step 2 of 5: …", "Step 2 passed: …", the runner's own message as the entry's detail), run finish and Automate result (AutomatePage reports its statuses) is an entry. `ActivityButton` toggles the in-window pane `ActivityPanel` (a UserControl over the right edge of the content layer, light-dismissed by a click elsewhere, Esc or its close button) with the filters All / This run / Errors (`ActivityFilterAll`, `ActivityFilterRun`, `ActivityFilterErrors`), `ActivityCopy` (Copy all) and `ActivityLogFolder`. Its list `ActivityList` is bound only while the pane is open, so its entries are in the UI Automation tree only then. "This run" is the run shown in Last run.
- Pages `LibraryPage`, `RunsPage`, `InspectorPage` and `SettingsPage` are declared in XAML and switched by `ShowPage` through `Visibility`; a page shown once stays in the UI Automation tree (offscreen) when hidden. The nav items' selected state is a `DataTrigger` on the page's `Visibility`.
- Automate is transient: `Workflows_Click` commits the editor, saves settings and builds a new `AutomatePage` (AutomatePage.cs) in `AutomateHost`. Every navigation goes through `ShowPage`, which calls `LeaveAutomate`: if Automate is running an operation it asks it to stop and stays; otherwise it stops the page's 2 s refresh, removes the page from the tree, and reloads settings, tests, the library and runs (what used to happen after the modal window closed). Automate's tabs have explicit AutomationIds and this order: `WorkflowTabJobs` (Background runs), `WorkflowTabSuites` (Test sets & data), `WorkflowTabMachines` (Virtual machines), `WorkflowTabDemonstrations` (Record), `WorkflowTabLifecycle` (Build, then test), `WorkflowTabProject` (Source code access), `WorkflowTabWorkspace` (Data & backup). Its status (`WorkflowStatus`) is an InfoBar with `StopWorkflow` and `WorkflowEvidence`; the raw result is in a Details expander shown only with technical details on.
- Flyouts (Change app, Help, Improve, the search results) are `Popup`s with `StaysOpen=True` and a code-behind light dismiss (a click elsewhere in the window, Esc, deactivation, moving or resizing the window); a Popup is a separate HWND only while open. Help holds Documentation (`HelpDocumentation`, opens the docs folder), the keyboard shortcuts (F5 Run, Shift+F5 Stop, Ctrl+N New test, Ctrl+S Save, Ctrl+D Duplicate, Delete (in the list) Delete, Ctrl+F Filter, Ctrl+K Search, Ctrl+1/2/3 Tests/Results/Automate, Ctrl+I Inspect controls, Ctrl+, Settings, F1 Help, Esc) and About (version, data folder). The shortcuts also appear in the tooltips of their commands.
- The step options dialog (`StepOptionsWindow`) stays a modal Fluent window.
- App icon: `src/Testy.Studio/Assets/Testy.ico` (a deep graphite rounded tile with white brackets and a green check, "[✓]"; 16, 20, 24, 32, 40, 48, 64 and 256 px, PNG-compressed; 16–24 px are a bold check with no or 1 px brackets). ### Show technical details

`StudioPreferences.Current.ShowTechnicalDetails` (StudioPreferences.cs) is the single app-wide flag, stored per Windows user in `%LOCALAPPDATA%\Testy\studio-user.json` (with `GettingStartedDismissed`, `McpListen`, `McpPort` and `McpToken`, see [Agent access](#agent-access-settings)) and bound TwoWay to `ShowTechnicalDetails`. Bind to it with `{Binding ShowTechnicalDetails, Source={x:Static local:StudioPreferences.Current}}` (also works on `DataGridColumn.Visibility`); code subscribes to `PropertyChanged`. Effects: the process ID and program on the app card; the raw Action, Selector and Value columns (with headers) of the steps editor and the Selector and wait-time fields of the step editor (also in Step options); the raw runner message under each step of Last run and a details box under the screenshot (message, action and selector, selector recovery, timing, screenshot path, failure diagnostics, run ID and folder); the Runner summary, Run ID and Run folder columns in Results; the JSON view; the log file path in the Activity pane; the status line's "N controls · step n" counters (`ContextStatus`); the scan source in the Inspect controls summary; and Automate's Details expander. Without it the Tests page reads as sentences with friendly control names and no selectors, enum names or paths. The Inspect controls page always shows its Control ID column (it is the page's purpose). Hidden option `--technical-details on|off` applies to one session without saving any preference (verify-studio starts Studio with `off`).

### Live workspace updates (changes made outside Studio)

Anything that writes the workspace while Studio is open (an AI agent through the MCP server, another Testy tool, a person editing a file) shows up without a restart. `WorkspaceWatcher` (WorkspaceWatcher.cs) keeps a `FileSystemWatcher` on `<workspace>\tests` and `<workspace>\runs` (`*.json`, so the store's `.tmp` files are ignored), debounces events (`ChangeDebounce` in Testy.Core: 300 ms after the last event, but at most 1 s after the first pending one, so a steady stream of writes still shows up while it goes on) and delivers one batch per pass on the Dispatcher. Studio's own saves never count as outside changes: `Persist` notes a SHA-256 of exactly what the store wrote (and `DeleteTest` notes the path; a delete that fails is forgotten again) in a `WorkspaceWriteLedger` (Testy.Core, unit-checked), and a file whose bytes match is skipped. Automate saves its suite runs and recorded drafts through the same `Persist`. `MainWindow.Workspace.cs` applies a batch:

- Every file is read tolerantly (`WorkspaceFiles.ReadTest`): a UTF-8 byte order mark is accepted, explicit nulls (`"category": null`, `"steps": [null]`, a step without a title) are normalised, and a test whose id or step ids are not valid is reported once in the activity log and left out. The same loader serves the startup load, Automate's return and Results (`LoadTestsTolerant`, `LoadRunsTolerant`): one bad file in `tests\` or `runs\` never keeps Studio from starting or refreshing. Files are mapped to test ids (`_testFileIds`, filled at load and on every read), so a test stored under another file name is recognised, a file rewritten with another id retires the test it held, and a test counts as deleted only when no remaining file holds it.
- Another test added, changed or deleted: the in-memory list is updated and the library rebound with the selection, the scroll position and, when the list had it, the keyboard focus kept (`RebindLibraryKeepingPlace`; ListItem names stay the test names). A file whose content equals the in-memory test is ignored.
- The selected test with a clean editor: reloaded in place, keeping the current view (Steps / Last run / JSON), the selected step, the shown run and the assistant's message. `LoadTest` builds the rows before it touches the screen and always releases its loading flag; a version that cannot be shown leaves the open one in place with a warning.
- The selected test with unsaved work: the edits stay and the warning InfoBar `ExternalChangeBar` ("This test was changed outside Studio…", accessible name "Changed outside Studio") offers **Reload** (`ReloadExternalChange`, loads the version on disk) and **Keep my edits** (`KeepMyEdits`; the next save replaces the file). "Unsaved work" is the dirty flag, JSON text that differs from the test, a step timeout typed but not applied, a grid cell still being edited, or a name or purpose that differs (`EditorHasUnsavedWork`). While the bar asks, nothing implicit decides: switching tests, running, New, Duplicate, opening Automate or a search result, and closing Studio are refused with the message "… was changed outside Studio. Choose Reload or Keep my edits above before leaving it." and the test stays open (the library filter only reads the editor meanwhile). Only **Save** (Ctrl+S) and Keep my edits replace the outside version; a save over it logs a Warning ("Saved “X” over the version an outside tool wrote.").
- The selected test deleted: it leaves the list, the editor keeps its copy (the state line reads "Not on disk: deleted outside Studio. Save or Save a copy keeps it." with the amber dot, also after further edits) and the same bar (accessible name "Deleted outside Studio", announced assertively) offers **Save a copy** (`SaveExternalDeleted`, a new test with a new id) and **Discard** (`DiscardExternalDeleted`). Implicit commits are refused the same way ("… was deleted outside Studio. Choose Save a copy or Discard above before leaving it (Save keeps it under its own id)."); **Save** and Apply JSON keep it under its own id. If the file comes back unchanged, the list shows it again and the state line reads "Saved"; if it comes back changed, the bar switches to the changed case. Deleting the test in Studio hides the bar in both cases. After a bar button, the keyboard focus moves to the name field (or the list) instead of vanishing with the collapsed button.
- While a Studio operation is in progress or one of Studio's modal dialogs is open (step options, file pickers), changes to the selected test wait and are applied when the operation or dialog ends; other tests update meanwhile. Improve refuses to overwrite a test that differs from the version the assistant saw; Step options edits the row that holds the step when the dialog closes, not the one it opened with.
- A run added or changed: `_runIndex` and the library's status texts update; Results refreshes when it is the visible page, keeping the selected row and scroll position (Results reloads on every navigation anyway); if the run belongs to the selected test, Last run shows the latest run again, unless a Studio operation is in progress (it refreshes when the operation ends) or a run is shown on purpose (opened from Results, or just produced by Studio): that run stays, and the status line says that a newer run exists.
- Activity entries (source `Workspace`): `Test “X” was added by an outside tool.`, `… was changed by an outside tool.`, `… was deleted by an outside tool.`, `… was replaced in its file by an outside tool.`, `Run of “X” finished (Passed) from an outside tool.` (the run entry carries the run id; a run that hasn't finished logs "started"). The test files carry no marker of who wrote them, so the wording stays generic.
- A file that can't be read yet (an agent mid-write, a lock, JSON that ends before it is complete) is skipped and read again on the next pass, up to six retries 500 ms apart; a complete file that is not a test is reported once and ignored until it changes; nothing is wiped because one file is unreadable. A watcher error (buffer overflow) re-creates the watcher and compares every file with what Studio shows. The watcher never changes busy state, disables nothing and opens no dialog; any problem, whatever its type, goes to the activity log and the rest of the batch is still applied.

### Apps named in words (new test from a description, Run)

`MainWindow.Apps.cs`, with the resolver in Testy.Core (`AppResolver`: pure scoring, ambiguity and the leading-clause parser) and discovery in Testy.Windows (`AppDiscovery`, `PackagedApps`), the same code the MCP server's `find_app` uses. The rules (candidates, scoring, the 0.7 threshold and 0.1 margin, packaged apps) are in [MCP.md](MCP.md#naming-the-app).

- **New test from a description.** When the description starts by naming its app ("In Customer Desk: …", "Using Order Desk, …", "Launch Customer Desk and …", or a first line "App: Customer Desk"; "open …"/"start …" are not read as app names), Studio resolves the name among running windows, installed apps, the apps saved tests use and the sample apps (Studio itself excluded; discovery runs off the UI thread). A clear match that is not the connected app, or any clear match when nothing is connected, is connected to, or started first (under the MCP server's launch policy: a local GUI `.exe` that is not a shell, terminal or script host; a packaged app only when the program its manifest names passes the same checks), inside the operation, before the scan and the planner. The planner gets the description without the app clause (so the Offline command parser reads "In Customer Desk: click id:ResetButton" as `click id:ResetButton`), and the new test stores the app: `TargetPath` (the .exe), `TargetName` (its friendly name) and, for a packaged app, `TargetAppId` (additive `TestCase` fields). An ambiguous name shows `AppChoiceBar` instead (below); a name that matches nothing keeps today's behaviour with the connected app (and an Activity entry), or, with nothing connected, an error that says how to name or connect the app. A description that names no app behaves exactly as before and stores nothing. Improve never resolves a name.
- **Run.** A test that stores its app runs there: when nothing is connected, the connected app has closed, or a different app is connected (not chosen by hand for this test), Run connects to the app's running instance or, when none runs, starts it (same policy), then runs; several running instances show `AppChoiceBar` with one button per window. A connection the person makes by hand (Change app › Connect, Open an app…, Sample app) while a test is selected is an override for that test's runs while that very process and window stay the connected one: Run uses it and logs a Warning that names both apps. Once Studio connects elsewhere (Run for another test connects to that test's app), the override no longer applies and the test runs in its own app again. The Activity log says which app a run used ("“X” runs in Customer Desk (started by Testy, process N).").
- **"Runs in".** `RunsIn` (the `RunsInText` TextBlock, now with an AutomationId) reads "Runs in {TargetName}" for a test that stores its app (the tooltip names the program and says Run connects to it or starts it), "Runs in {connected app} (chosen with Change app; the test names {app})" during a manual override, and the connected app's name (or "the connected app") for a test that stores none. Open an app… also stores `TargetName` with the path.
- **AppChoiceBar** (a UserControl under the editor's message bar, collapsed until needed, so it is in the UI Automation tree only while it asks): `AppChoiceText` (polite live region), up to five buttons `AppChoice1`…`AppChoice5` (name and kind: "running, process N" (two windows of one app usually share a title), "installed", "installed (Store app)", "sample app"; the tooltip has the window title and the program) and `DismissAppChoice`. Choosing a button continues the create or the run with that app; nothing is disabled while it shows and no dialog or window opens. It closes when another test is loaded.
- **Cleanup.** Apps Studio started for a test close with Studio (their main window is asked to close), like the sample app; a started sample app becomes Studio's sample-app process, so Sample app reconnects to it. Apps the person started are never closed.

### Agent access (Settings)

The last section of Settings, "Agent access (MCP)", is one card (MainWindow.AgentAccess.cs, McpAccess.cs) with no product-specific wording: "Let AI agents on this PC create and run tests in Testy through the Model Context Protocol (MCP)." and "Any MCP-capable agent can connect; nothing is tied to a particular tool."

- `McpStatus` (TextBlock, a polite live region): whether the server executable was found (`Testy.Cli.exe` next to Studio in the bundle, or the development build through the same lookup as `StudioCommandClient`, with a `dotnet Testy.Cli.dll` form when only the dll exists) and the listener state: "Server found: … Not listening; …", "Listening for agents at http://127.0.0.1:PORT/mcp (server process PID, token required). …", or a start failure. The result of Test the connection ("Testy answered with N tools (every native and Cortex tool) in 0.2 s …", "No answer from the server: …" with the server's last log lines) goes to the status line and the activity log; the card shows it only while nothing is listening.
- `McpCommand` (read-only mono TextBox): `"<full path>\Testy.Cli.exe" mcp --workspace "<workspace>"`, quoted by the Windows command-line rules (a trailing backslash is doubled; a workspace loses its trailing separator except a drive root); **Copy command** (`CopyMcpCommand`) and **Copy JSON** (`CopyMcpJson`: a common MCP client configuration shape `{"mcpServers":{"testy":{"command":"…","args":["mcp","--workspace","…"]}}}`, pretty-printed; the development build adds `"env":{"DOTNET_ROOT":"…"}` when the apphost needs it, and the help text under the command says so). The help text also states that the server can start desktop programs and send input to the app an agent names, with the person's rights.
- **Listen for agents (HTTP)** (`McpListen`, the `ToggleSwitch` style): on, Studio starts `Testy.Cli.exe mcp --transport http --port <port> --workspace "<ws>"` as a hidden child (`McpListener`) with the bearer token in its environment (`TESTY_MCP_TOKEN`, never on the command line), reads its one JSON startup line (it must report `tokenRequired: true`) and shows the URL in `McpUrl` (read-only TextBox, empty while not listening) with **Copy URL** (`CopyMcpUrl`) and **Copy HTTP JSON** (`CopyMcpHttpJson`: an `mcpServers` entry with `"type":"http"`, the URL and the token as its `Authorization` header). `McpPort` (a NumberBox, `LostFocus`): the port for the next start, `StudioPreferences.McpPort`; 0 lets Windows pick a free one, which is then kept, so an agent's saved address stays valid across restarts; a remembered port that is taken falls back to a free one with a Warning entry. `McpToken` (read-only, shows "Bearer token required · ends in xxxx", never the whole token) with **Copy token** (`CopyMcpToken`); the token is `StudioPreferences.McpToken`, generated once per Windows user. While listening the server writes `<workspace>\mcp\endpoint.json` (url, port, tokenRequired, pid, startedAt; never the token) and removes it when it stops. Off waits for the server's own orderly stop (up to 25 s, awaited, so a run in progress is saved and apps launched with `keepOpen` survive; the status line says "Stopping the server…"), then kills the server process only; closing Studio waits 5 s. The switch is remembered per user (`StudioPreferences.McpListen`) and the listener starts again at launch. A failed start, or a server that ends on its own, turns the switch off for this session only (the preference stays, so the next start retries) and `McpStatus` says so; a stop that is still under way when Studio closes is stopped as well (`_mcpGeneration`). The child's stdout is drained and discarded; its stderr goes to the activity log (source `Agent access`): warnings and errors always, ordinary lines at most one every 5 s.
- **Test the connection** (`TestMcpConnection`): starts a stdio server the way an agent does, sends `initialize` + `tools/list` (`McpStdioSession`), then closes it; async, no busy state, nothing disabled (a second click while one runs is ignored); a server that offers no tools fails the test. **Open guide** (`OpenMcpGuide`) opens `docs\MCP.md`, or `AGENT-ACCESS.md` at the bundle root, with the shell; on a PC with no program for `.md` files it shows the file in its folder instead and says so.
- Hidden options `--mcp-listen on|off`, `--mcp-port N` and `--mcp-token T` set the switch, the port and the token for one session without saving any preference (every verifier starts Studio with `--mcp-listen off` and `--technical-details off` through `StudioLaunch`; verify-studio adds a token of its own). Screenshot mode saves no preference either.

### Hidden review options

`--screenshot-dir DIR --screenshot-pages tests,lastrun,running,activity,search,improve,json,results,inspect,settings,agentaccess,externalchange,automate[:<tab AutomationId>],help,changeapp,stepoptions [--screenshot-prefix NAME] [--screenshot-setup none|lab|run] [--screenshot-test NAME]`, used with a scratch `--workspace` and `--theme light|dark`, captures each page from the screen (Mica and flyouts included) and closes Studio. `run` connects the sample app and replays "Create a customer" (or the sample named by `--screenshot-test`) with replay settings kept in memory only; `running` captures a replay while it runs; `agentaccess` is Settings scrolled to the Agent access card with the HTTP listener on; `externalchange` gives the selected test an unsaved edit, changes it through the real MCP server (`update_test`) and captures the "changed outside Studio" bar; `screenshots` is kept as another name for `lastrun`.

## Portable layout

The full publish script puts `Testy.Studio.exe`, `Testy.Cli.exe`, `Testy.TestLab.exe`, `Testy.OrderLab.exe` and `Testy.WpfLab.exe` together in `dist/Testy`. Resolve the Customer Desk lab from `Path.Combine(AppContext.BaseDirectory, "Testy.TestLab.exe")` before development-only fallback paths. Backend-only publication goes to the separate `dist/Testy.Backend` directory and does not build or publish Studio.

The API adapters are protocol-tested without API credentials. Codex is the provider used for actual AI calls during development. Studio serializes attachment, inspection, planning, execution, and analysis; it retains the originating test/run identity across awaits and preserves drafts when saving fails. See the final verification report for actual GUI and live-provider checks.
